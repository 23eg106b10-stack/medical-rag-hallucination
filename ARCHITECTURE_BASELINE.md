## 4. Layer Architecture

The system is organized into four horizontal layers. Each layer may only depend on layers below it; no upward dependencies are permitted.

```
┌─────────────────────────────────────────────────────────────┐
│                   Application Layer                          │
│   app/   evaluation/   scripts/                             │
├─────────────────────────────────────────────────────────────┤
│                   Pipeline Layer                             │
│   generation/   verification/   retrieval/   index/         │
├─────────────────────────────────────────────────────────────┤
│                 Schema / Contract Layer                      │
│                      schemas/                               │
├─────────────────────────────────────────────────────────────┤
│                 Infrastructure Layer                         │
│             config/   utils/   data/                        │
└─────────────────────────────────────────────────────────────┘
```

**Cross-cutting rules:**

- `config/settings.py` is the **only** module permitted to read environment variables. All other modules receive configuration exclusively through the `get_settings()` singleton.
- `utils/logging.py` is the **only** module permitted to configure logging handlers and format. All other modules call `logging.getLogger(__name__)` only and never call `logging.basicConfig()`.
- Settings fields are added **only in the milestone that first requires them**. Fields are not front-loaded.

## 5. Component Specifications (by milestone)

### 5.1 M3.1.1 — Corpus Construction

**Module:** `index/corpus_pipeline.py`, `index/corpus_sources.py`  
**Entry point:** `index/build_corpus.py`  
**Spec:** `docs/m3-corpus-construction-architecture.md`

**Responsibilities (exactly five):**
1. Obtain PubMed abstracts via two sources
2. Normalize retrieved metadata
3. Deduplicate by PMID
4. Validate documents
5. Export a frozen, versioned corpus

**Inputs:**
- Source A: PubMedQA (`data/pubmedqa/ori_pqal.json`) — provides PMID coverage list
- Source B: NCBI E-utilities — provides actual metadata (authoritative source for PMID deduplication)
- `config/queries.yaml` — frozen, versioned MeSH query specification; consumed, never modified

**Deduplication rule:** PMID is the primary key. When the same PMID appears in both sources, NCBI E-utilities (Source B) is the retained record. No fuzzy matching.

**Validation rule:** PMID, title, and abstract must all be non-empty and meaningful. Invalid records are skipped; no repair is attempted.

**Outputs:**

| File | Description |
|---|---|
| `data/corpus/corpus.jsonl` | Frozen corpus — one JSON document per line |
| `data/corpus/corpus.meta.json` | Corpus metadata record |

**Canonical document schema (`schemas/corpus.py`):**
```python
class CorpusDocument(BaseModel):
    pmid: str
    title: str
    abstract: str
```
No embedding, score, or ranking fields.

**Corpus metadata schema (`schemas/corpus.py`):**
```python
class CorpusMetadata(BaseModel):
    corpus_version: str
    generated_at: str
    document_count: int
    checksum_sha256: str
```

**Error boundary:** Corpus generation either completes fully (producing both `corpus.jsonl` and `corpus.meta.json`) or fails and produces no output. Partial output is not valid.

### 5.2 M3.1.2 — BM25 Index Building

**Module:** `index/bm25_pipeline.py`  
**Entry point:** `index/build_bm25.py`  
**Tokenizer:** `index/bm25_tokenizer.py` (shared with `retrieval/sparse.py` — same tokenizer must be used at build and query time)  
**Algorithm:** `rank_bm25.BM25Okapi`, version pinned as `"BM25Okapi"` in metadata  

**Input:** `data/corpus/corpus.jsonl` (M3.1.1 output)

**Outputs:**

| File | Description |
|---|---|
| `data/indexes/bm25_index.json` | Pickled `{"model": BM25Okapi, "pmids": [...]}` |
| `data/indexes/bm25_metadata.json` | `BM25Metadata` record |

**BM25 metadata schema (`schemas/bm25.py`):**
```python
class BM25Metadata(BaseModel):
    bm25_version: str
    corpus_version: str
    document_count: int
    tokenizer: str
    algorithm: str
    library: str
    created_at: str
```

**Index payload contract:** The pickle contains a dict with exactly two keys: `"model"` (a `BM25Okapi` instance) and `"pmids"` (a `list[str]`). The `pmids` list is ordered identically to the model's internal document positions — this is the ordering contract that `BM25Retriever.from_pickle` depends on.

### 5.3 M3.1.3 — Dense (FAISS) Index Building

**Module:** `index/faiss_pipeline.py`, `index/embedding_generator.py`  
**Entry point:** `index/build_faiss.py`  
**Model (document-side):** `ncbi/MedCPT-Article-Encoder` (configurable via `settings.medcpt_model_name`)  
**Index type:** `faiss.IndexFlatIP` (exact cosine similarity via pre-normalized L2 inner product)  
**Embedding dtype:** `float32`  
**Normalization:** L2, applied before index insertion (per ADR-001)  

**Document text for embedding:** `f"{title} {abstract}"` (title + abstract concatenation, matches BM25 representation)

**Input:** `data/corpus/corpus.jsonl` + `data/corpus/corpus.meta.json`

**Outputs (three-file artifact set — all three must be present together):**

| File | Description |
|---|---|
| `data/indexes/faiss_index.bin` | The FAISS `IndexFlatIP` |
| `data/indexes/embedding_metadata.json` | `EmbeddingMetadata` record |
| `data/indexes/faiss_pmids.json` | `list[str]` — PMIDs in vector-position order |

`faiss_pmids.json` was added by **ACR-001** (M3.1.3 architecture change request, raised during M3.2 implementation). It provides the explicit, corpus-independent mapping from FAISS vector position `i` → PMID. Without it, retrieval code would have to re-read `corpus.jsonl` or depend on the BM25 artifact for ordering — both approaches were explicitly rejected.

**Embedding metadata schema (`schemas/embedding.py`):**
```python
class EmbeddingMetadata(BaseModel):
    embedding_version: str
    corpus_version: str
    corpus_checksum: str     # copied verbatim from corpus.meta.json
    model_name: str
    embedding_dimension: int
    embedding_dtype: str
    faiss_index_type: str
    normalize_embeddings: bool
    document_count: int
    created_at: str
```

**Corpus/index integrity contract:** `corpus_checksum` is copied from `corpus.meta.json` into `embedding_metadata.json` at build time. Future retrieval components (and the FAISS pipeline's own `load_corpus_metadata`) may cross-check this before trusting a loaded index.

**Error boundary:** All three files are written to temporary paths first, then atomically renamed into place. If any write fails, all temp files and any partially-renamed final files are removed. A missing or partial artifact set is not valid.

**Three-way consistency check (load time):** `DenseRetriever.from_disk` validates that `len(faiss_pmids) == index.ntotal == embedding_metadata.document_count`. A mismatch raises `ValueError` immediately, before any query is served.

### 5.4 M3.2 — Hybrid Retrieval

**Modules:** `retrieval/retriever.py`, `retrieval/sparse.py`, `retrieval/dense.py`, `retrieval/fusion.py`, `retrieval/corpus.py`

#### Design principles

- **Dependency injection everywhere.** `HybridRetriever` accepts already-constructed `BM25Retriever`, `DenseRetriever`, and `InMemoryCorpusReader` instances. It owns no loading logic.
- **Rank assignment is owned by the retriever, not the fusion layer.** `BM25Retriever.search` and `DenseRetriever.search` both apply deterministic sorting (score descending, PMID ascending on ties) and assign 1-indexed `rank` values on each `RetrievalHit` before returning. The fusion function consumes explicit ranks — it never infers rank from list position or dict iteration order.
- **Fusion is corpus-independent.** `reciprocal_rank_fusion` operates only on `RetrievalHit` metadata. It never touches corpus text.
- **In-memory corpus lookup.** `InMemoryCorpusReader` loads `corpus.jsonl` into a `dict[str, CorpusDocument]` at startup, trading startup memory for O(1) lookup. SQLite conversion and byte-offset seeking were explicitly rejected.
- **Missing PMID is always a fatal error.** `InMemoryCorpusReader.get_documents` raises `MissingDocumentError` if any requested PMID is absent. Silent omission is never acceptable — it indicates index/corpus drift.

#### Retrieval schema (`schemas/retrieval.py`)

```python
class RetrievalHit(BaseModel):
    pmid: str
    score: float
    rank: int                        # 1-indexed, assigned by the retriever

class FusionResult(BaseModel):
    pmid: str
    rrf_score: float
    sparse_score: float | None       # None = not in sparse Top-20
    dense_score: float | None        # None = not in dense Top-20

class HybridScoredDocument(BaseModel):
    document: CorpusDocument
    sparse_score: float | None
    dense_score: float | None
    rrf_score: float
```

#### Fixed hyperparameters (frozen at M3.2)

| Parameter | Value | Location |
|---|---|---|
| Sparse pool size | 20 | `retrieval/retriever.py` — `_SPARSE_TOP_K` |
| Dense pool size | 20 | `retrieval/retriever.py` — `_DENSE_TOP_K` |
| RRF constant k | 60 | `retrieval/fusion.py` — default argument |
| Final result count | 5 | `retrieval/retriever.py` — `_FINAL_TOP_N` |

These are architectural constants, not configuration. They must not be read from settings without a corresponding ADR.

#### RRF formula

```
rrf_score(pmid) = Σ  1 / (k + rank_i(pmid))
                 i ∈ {sparse, dense}
                 (term omitted if pmid absent from retriever i's pool)
```

`k = 60` (standard Cormack et al. 2009 value).

Result list is sorted by `rrf_score` descending, PMID ascending on ties, before being returned. Callers may safely slice `[:5]` without re-sorting.

#### Query-side encoder

- Model: `ncbi/MedCPT-Query-Encoder` (configurable via `settings.medcpt_query_encoder_model_name`)
- Distinct from the document-side encoder (`ncbi/MedCPT-Article-Encoder`) used to build the FAISS index
- Query vector is L2-normalized before `IndexFlatIP.search`, matching the normalization applied at index build time

#### Fewer-than-5-results contract

If RRF fusion produces fewer than `_FINAL_TOP_N` unique PMIDs, `HybridRetriever.search` logs a warning and returns what is available. No exception is raised.

### 5.5 M3.3 — LLM Generation

**Modules:** `generation/generator.py`, `generation/context_builder.py`, `generation/prompts.py`, `generation/llm_loader.py`  
**Entry point:** Not yet built. Full pipeline wiring (`HybridRetriever` output → `Generator` input) is deliberately deferred until Claim Extraction and Verification also exist — see §10.  
**Inference backend:** Hugging Face Transformers + bitsandbytes, 4-bit quantization — mandatory, per **ADR-M3.3-001**  
**Model:** `meta-llama/Llama-3.1-8B-Instruct` (configurable via `settings.llm_model_name`)

#### Design principles

- **Dependency injection everywhere**, consistent with `retrieval/`. `Generator` accepts an already-loaded `model`, `tokenizer`, an injected `context_builder` callable, and an injected `generate_fn` callable. It owns no loading or prompt-assembly logic itself.
- **Prompt template ownership is split by responsibility, per ADR-M3.3-002.** `generation/prompts.py` holds only declarative template constants — no string concatenation, formatting, context assembly, or truncation logic is permitted there. All assembly logic lives exclusively in `generation/context_builder.py`.
- **Loading is separate from generation.** `generation/llm_loader.py` is responsible only for loading the tokenizer and model, mirroring the pattern already established by `index/embedding_generator.py`. The concrete generation call (`make_transformers_generate_fn`) lives in `generation/generator.py` instead — loading and generating are distinct responsibilities.
- **No silent context truncation.** `PromptBuilder` raises `PromptOverflowError` when the assembled prompt exceeds its configured token budget. Evidence is never silently dropped to make a prompt fit — see ACR-002 below.
- **Deterministic generation by default, per ADR-M3.3-004.** `do_sample=False` (greedy decoding) is the default, for reproducible evaluation runs.
- **`GeneratedAnswer` is a dedicated schema, not a reuse of `AnswerResponse`.** `AnswerResponse` is the pipeline's final, post-verification, user-facing answer shape. `GeneratedAnswer` is raw, pre-verification model output that must carry retrieval context forward for downstream claim extraction — reusing `AnswerResponse` would overload a schema whose name implies a trust level this data hasn't earned yet.
- **Fail-loud on empty output.** `Generator.generate` raises `EmptyGenerationError` rather than ever returning a `GeneratedAnswer` with empty `answer_text`.

#### Generation schema (`schemas/generation.py`)

```python
class GeneratedAnswer(BaseModel):
    question: str
    answer_text: str
    context: list[HybridScoredDocument]
    model_name: str
```

No `generated_at` field. `GeneratedAnswer` is runtime data, not a persisted artifact — unlike `CorpusMetadata`, `BM25Metadata`, and `EmbeddingMetadata`, which describe artifacts written to disk. If answers become persisted in a later milestone, a distinct record type should carry that timestamp, not this schema.

#### Prompt structure

Fields are assembled in a fixed order: **System → Evidence → Question → Answer.**

#### Failure boundaries

| Condition | Behavior |
|---|---|
| Empty or whitespace-only model output | `Generator.generate` raises `EmptyGenerationError`. No empty `GeneratedAnswer` is ever returned. |
| Prompt exceeds `context_window` tokens | `PromptBuilder.build_prompt` raises `PromptOverflowError`. No truncation. |
| Model/tokenizer fails to load | `llm_loader.load_generation_model` raises `RuntimeError`. No partial or fallback model is returned. |

---

#### ACR-002 — PromptBuilder Architecture

**Previous design:** `build_prompt()` was a free function — `build_prompt(question: str, context: list[HybridScoredDocument]) -> str`.

**Problem:** The tokenizer and context window were hidden dependencies. The function's signature had no parameter through which to receive either, so prompt token budgeting could not be enforced cleanly — this directly conflicted with the frozen no-silent-truncation failure boundary, which requires counting tokens against a real tokenizer.

**New design:** `PromptBuilder` is now a class, constructed with:
- `tokenizer` — the loaded tokenizer used for token counting
- `context_window` — the maximum permitted prompt token count

`build_prompt()` is now an instance method. `Generator` remains unchanged: the bound method `PromptBuilder(...).build_prompt` satisfies the existing dependency injection contract (`Callable[[str, list[HybridScoredDocument]], str]`) with no modification to `generator.py`.

**Responsibilities of `PromptBuilder`:**
- Prompt assembly
- Prompt token counting
- Context-window validation
- Raising `PromptOverflowError` on overflow

**Explicitly:**
- `PromptBuilder` never truncates evidence.
- Overflow is treated as an error, never as a signal to silently modify the prompt.

Full ACR text: [`ARCHITECTURE_CHANGE_REQUESTS.md`](./ARCHITECTURE_CHANGE_REQUESTS.md)

---

#### Known Limitations

**Prompt Budget Scope.** `PromptBuilder` validates only the prompt token budget. It does not currently reserve generation headroom for `max_new_tokens`. A prompt that satisfies `context_window` may still cause the model's effective context limit to be exceeded during generation, if `prompt_length + generated_tokens` exceeds model capacity. This is an accepted limitation for M3.3 and may be addressed by a future architectural revision.

### 5.6 M4 — Claim Extraction

**Modules:** `verification/claim_extraction_prompts.py`, `verification/claim_extraction.py`, `schemas/verification.py`<br>
**Entry point:** Not yet built (full verification pipeline orchestrator deferred to M5).<br>
**Underlying model:** `meta-llama/Llama-3.1-8B-Instruct` (reused from M3.3 via `generation.llm_loader.load_generation_model`, per ADR-M3.3-001 and ADR-M4-003 §1)<br>
**Decomposition mechanism:** LLM-based decomposition (`do_sample=False` greedy decoding, ADR-M4-003 §1, §2)

#### Design principles

- **Verification unit = atomic medical claim, per ADR-M4-001.** The verification unit throughout the verification pipeline is the individual atomic medical proposition rather than the natural-language sentence.
- **Verification-side evidence attribution, per ADR-M4-002.** Claim extraction does not extract, assign, or output cited passage IDs. `ExtractedClaim` holds only `claim_text: str`. Evidence attribution is performed downstream during M5 NLI verification against `GeneratedAnswer.context`.
- **Low-fragility plain-text output, per ADR-M4-003 §4.** The extraction model is prompted to emit one claim per line in plain text — explicitly NOT JSON or a delimited format — avoiding format-reliability failures on 8B quantized models.
- **Strict separation of prompt constants and parsing logic, per ADR-M4-003 §3.** `verification/claim_extraction_prompts.py` contains only declarative prompt template constants. All line splitting, bullet stripping, fragment filtering, commentary filtering, and deduplication logic lives in `verification/claim_extraction.py`.
- **Deterministic parsing and filtering contract, per ADR-M4-003 §5.**
  1. Split raw output on newlines.
  2. Strip each line of leading numbering/bullet markers (e.g. `1.`, `-`, `*`) and surrounding whitespace.
  3. Discard blank lines.
  4. Post-hoc strip inline citation markers (e.g. `[PMID: ...]`, `(PMID: ...)`, `(References: [PMID: ...])`). Citation stripping is not delegated to prompt compliance.
  5. Discard incomplete fragments via observable string-level rules: discard if the line does not end in terminal sentence punctuation (`.`, `!`, `?` or trailing quote/parenthesis) or contains unbalanced brackets/parentheses.
  6. Discard conversational / generation-process commentary (statements about the model's own response, behavior, apologies, or rephrasing offers; substantive claims regarding evidentiary uncertainty are retained).
  7. Deduplicate via string-level normalization only: lowercase, strip punctuation, collapse whitespace, exact-match comparison. No semantic embeddings, stemming, or lemmatization.
- **Atomicity and anaphora resolution are a generation-prompt contract, per ADR-M4-003 §6.** The extraction prompt requires the model to emit already-atomic, already-resolved propositions with anaphoric referents grounded. The parser performs no downstream semantic decomposition or atomicity detection.
- **Claim-count safety bound (`MAX_CLAIMS = 35`), per ADR-M4-003 §7, §8.** Evaluated on the post-filter, post-dedup unique valid claim count. 0 valid claims is valid (e.g. answer is pure commentary); 1..35 valid claims is valid; >35 valid claims raises `ClaimExtractionError` with no silent truncation. Calibrated empirically against real pipeline answers (N=10 calibration max = 24, +45.8% safety margin, sitting above $\mu + 3\sigma$).
- **Fail-loud on malformed output, per ADR-M4-003 §9.** If raw output yields 0 candidate lines after initial line-splitting and blank discard (e.g. empty or whitespace-only generation), `ClaimExtractionError` is raised. No silent fallback to treating the unparsed answer text as a single claim.

#### Verification schema (`schemas/verification.py`)

```python
class ExtractedClaim(BaseModel):
    claim_text: str
```

#### Failure boundaries

| Condition | Behavior |
|---|---|
| Empty or whitespace-only extraction output (0 candidate lines) | `ClaimExtractionError` raised. No unparsed text fallback. |
| Post-filter unique claims > 35 | `ClaimExtractionError` raised. No silent truncation to 35. |
| Incomplete fragment or unclosed bracket/parenthesis | Line discarded by parser rule 5(a)/(b). |
| Conversational / generation-process commentary | Line discarded by parser rule 5(c). |

## 8. Infrastructure Standards

These standards apply globally. They are invariant across milestones unless an ADR explicitly supersedes one.

### 8.1 Settings

- `config/settings.py` (`get_settings()`) is the **only** permitted source of runtime configuration.
- No module outside `config/settings.py` may call `os.getenv`, `os.environ`, or `dotenv`.
- Settings fields are introduced only in the milestone that first requires them.

### 8.2 Logging

- `utils/logging.py` (`setup_logging()`) is the **only** place that configures logging handlers and format.
- Every other module calls only `logging.getLogger(__name__)`.
- `logging.basicConfig()` is never called outside `utils/logging.py`.
- `setup_logging()` is idempotent: safe to call multiple times (uses `_HANDLER_MARKER` sentinel).
- Entry points call `setup_logging()` exactly once, before doing anything else.
- Log format: `"%(asctime)s | %(levelname)-8s | %(name)s | %(message)s"`
- Rotating file handler: 10 MB per file, 5 backups.

### 8.3 Error boundaries

- Index-building pipelines produce either complete output or no output. Partial artifacts are always removed.
- Retrieval pipelines raise immediately on index/corpus inconsistency; they never silently degrade.
- Corpus construction raises and stops on network interruption; it does not attempt partial saves.

### 8.4 Determinism

- BM25 and dense retrievers sort by `(score descending, PMID ascending)` before assigning ranks. FAISS's native result order is not trusted for rank assignment.
- RRF fusion sorts by `(rrf_score descending, PMID ascending)` before returning.
- The BM25 tokenizer (`index/bm25_tokenizer.py`) is shared between index building and retrieval to guarantee identical tokenization at query time.

### 8.5 Dependency injection

- `HybridRetriever` accepts pre-built retriever and reader instances; it owns no I/O.
- `DenseRetriever` accepts an injected `encode_fn: Callable[[str, Any, Any], np.ndarray]`; it does not hardcode a specific encoding routine.
- `BM25Retriever` accepts an injected `tokenizer: Callable[[str], list[str]]`; callers are responsible for sourcing it from `index.bm25_tokenizer`.
- `Generator` accepts injected `model`, `tokenizer`, `context_builder`, and `generate_fn`; it owns no loading or prompt-assembly logic. `PromptBuilder` accepts an injected `tokenizer` and `context_window` at construction (ACR-002), rather than hardcoding either.

### 8.6 Schema placement

| Schema | File | Notes |
|---|---|---|
| `Document`, `RetrievedDocument` | `schemas/common.py` | Scaffolding-era generic types |
| `CorpusDocument`, `CorpusMetadata` | `schemas/corpus.py` | Corpus-specific; no score/embedding fields |
| `BM25Metadata` | `schemas/bm25.py` | BM25 index audit record |
| `EmbeddingMetadata` | `schemas/embedding.py` | FAISS index audit record |
| `RetrievalHit`, `FusionResult`, `HybridScoredDocument` | `schemas/retrieval.py` | Retrieval-specific; carry ranking/fusion metadata |
| `GeneratedAnswer` | `schemas/generation.py` | Pre-verification generation output; distinct from `AnswerResponse` |
| `ExtractedClaim` | `schemas/verification.py` | Atomic medical claim verification unit (M4; ADR-M4-001, ADR-M4-002, ADR-M4-003) |

Retrieval result schemas are separate from corpus schemas by design: retrieval results carry rank, score, and fusion metadata that has no place on a `CorpusDocument`.
